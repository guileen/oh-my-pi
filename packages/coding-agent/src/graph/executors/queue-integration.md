# External queue host integration

The Graph code does not ship a queue service or select a provider. Install a `QueueIntegration` only from trusted host configuration after selecting and authorizing an existing service. Graph definitions, task text and callbacks must not register clients or change credentials, service identity, capability claims, callback verification, or host authorization policy. There is no default service or network listener; an unconfigured queue node fails closed.

Implement `QueueServiceClient` for the chosen service's actual API. Set a stable, unique `service_id`; report `submit_idempotent`, `lookup_by_key`, and `cancel` only when the service guarantees them for the relevant retention period and operation. The client must send the original request key and attempt/fence identity on submission, use that same key for lookup, and normalize authenticated service replies into `QueueObservation`. Never treat a submit receipt as task completion. A transport error or malformed reply leaves the outcome unknown. Services without authoritative lookup and idempotence cannot be retried automatically after a lost receipt.

If a submission or lookup fails while newer evidence is recorded, reconciliation preserves that newer record rather than replacing it with an unknown state. This does not make a lost receipt proof of completion or remove the need for an authoritative lookup.

Use the profile's `GraphRunStore` as the durable `QueueStateStore`; do not create a second queue schema. Its immediate transactions serialize request-key mutations. The quarantine table can contain sensitive evidence and is governed by the Graph profile's database permissions and retention. Construct `QueueIntegration` with this store, the service client, a callback protocol, and `resolveCurrent`. Service credentials, TLS settings, and service-specific timeouts belong in trusted client configuration, not task data.

Once a correlated submission has settled, the invocation becomes durably `waiting` and releases Graph execution capacity; the shared queue still owns its resource limits. Submission in flight remains `running`. Queue progress and opted-in wire replacements commit in the same transaction, with `wait_reason: queue:<state>`; a remote terminal state remains waiting for Host verification, not dependency success. Exact attempt/envelope matching is shared by recovery, completion and observation. Duplicate observations and read-only lookups do not publish new feed events. This does not enable standalone execution, provide a queue service or expose raw remote task IDs.

The callback protocol must authenticate the exact request bytes and relevant headers using the selected service's documented signature scheme, credential rotation, and replay policy before decoding. Verification must fail closed. The HTTP endpoint must enforce HTTPS, restrict access appropriately, and impose a streaming request-size limit before buffering; `maxCallbackBytes` is an additional in-process bound, not a streaming limit. Decode only authenticated data and map it to an observation containing the original service, request key, attempt, fence and external task identity. `resolveCurrent` must independently check the current authorized host attempt and its fence in trusted run state; it must not simply echo the callback's identity. Unknown, stale, mismatched or conflicting evidence is quarantined rather than advancing a Run. Duplicate terminal observations are idempotent.

`resolveCurrent` and the queue record update are separate transactions: they do not fence Run advancement. The Host must atomically recheck the current Run attempt and fence when accepting a result, including after a callback was accepted by this adapter.

Configure `GraphHostOptions.queue` with the integration, a frozen-request resolver, an authorization check, a result verifier and, for outputs, an artifact-registration preparer. The verifier maps confirmed terminal service results to Graph completion metadata; its output references must exactly match those reported by the service. The preparer must independently verify authorization, availability, size, digest, media contract and provenance before registration. The host checks request identity and frozen executor, persists dispatch, reconciles durable queue records after restart, records cancellation as intent, and commits verified terminal results under the current owner and attempt fence. `acceptCallback` records authenticated evidence; the next host tick reconciles it. An adapter result alone does not authorize Graph advancement. A real end-to-end acceptance test requires an approved service and worker; callback fixtures do not prove one exists.
