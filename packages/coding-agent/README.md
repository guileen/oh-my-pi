## Named headless Bots

Bots are fixed capability definitions; each submission creates an isolated Job. No coding-agent prompt, project rules, tools, Skills or extensions load unless configured.

```bash
omp bot create reviewer --system-prompt ./reviewer.md --tools read,grep --cwd ./project
omp bot reviewer submit "Review cancellation behavior" --request-key review-123 --json
omp bot reviewer watch JOB_ID --json
omp bot reviewer send JOB_ID "Check timeout cleanup" --json
omp bot reviewer compact JOB_ID --mode qaonly --json
omp bot reviewer stop JOB_ID --json
```

Submission/control receipts return before model completion. Query `request REQUEST_ID` for application and `status JOB_ID` for execution state; `idle` is not business acceptance. Observers can reconnect using `watch --since '<cursor>'`. Work survives viewer disconnection; filesystem/network isolation remains the caller's sandbox responsibility. See the [command and wire contract](../../docs/bot-observability-spec.md).

For automation, pass `--expect-bot-id BOT_ID` on named operations and `inspect REF --job JOB_ID` for scoped details. Snapshots advertise supported capabilities and include recoverable questions, reply reservations and execution ownership. Compaction waits safely for required answers; timeout/background continuations reacquire Bot capacity. A stopped Job can retain a closed activation reference as history.

Graph consultation is available only when a trusted Graph host installs its consultation authority and continuation gate. `graph_ask`, `graph_question`, and `graph_reply` wait for the next authorized message or a timeout; `graph_finish` closes the consultation. Waiting releases the Graph compute slot and retains the live Bot continuation. If that live continuation is lost, the host records an unknown result rather than replaying the tool stack. This mechanism is not an OS sandbox and does not supply production authorization.

The Bot database upgrades to schema 2 with a private standalone backup; stop legacy workers first. Existing IDs, request keys and historical references survive. Uncertain crash-owned work requires reconciliation, never automatic replay. A trusted Graph host retries cleanup with a retained Bot lease and pending receipt; other work for that Bot waits until cleanup succeeds, the lease is lost, or the host shuts down. External Graph/PWA integration remains separate and requires its actual host repository.

Runtime verification and remaining external integration gates are tracked in [OpenSpec: harden-bot-graph-observation](../../openspec/changes/harden-bot-graph-observation/tasks.md). Existing herdr terminal support is not a Graph PWA adapter.

Unix non-PTY services run under an authenticated per-generation supervisor retaining native child ownership. Broker restarts reconnect to that owner; persisted PIDs are diagnostic only. Legacy records and lost supervisors remain `unknown`, reserve their service name and cannot be automatically replaced, restarted or signalled. Reconcile them externally before removing stale metadata. PTY and Windows processes are not durably adopted after broker loss. `omp ps` inspects offline state without starting a broker; unknown ownership has no inferred uptime. Supervisor process groups are not descendant containment, so this does not enable standalone Graph execution.

Service responses reporting exit wait for the generation's durable completion publication. A resumed session can replay its pending completion even when terminal metadata writes are slow; snapshots returned over IPC do not change while persistence is awaited.

## Local foreground Graph runs

The current Graph milestone is a local, trusted single-user workflow, not the full orchestration platform. Import the packaged two-Bot example, then use its returned Graph ID:

```sh
omp graph import --file packages/coding-agent/examples/graph/local-text-handoff/GRAPH.md --request-key local-example
omp graph run GRAPH_ID \
  --bindings packages/coding-agent/examples/graph/local-text-handoff/models.md \
  --input task=packages/coding-agent/examples/graph/local-text-handoff/task.md \
  --max-model-calls 8 --timeout-ms 180000 --request-key local-trial-1
```

The example declares `task` as a required run input and `omp graph list` reports it as `in:task`; omit it and the Run is rejected during preflight instead of running against a hardcoded brief.

A local Run may also write files and run checks. `examples/graph/local-code-slice` declares a coding member with `read: **`, `write: src/**`, `test/**` and the single `test` execute grant; launch it from inside the target workspace, because the workspace root is the foreground process directory and every grant is relative to it. Admission replaces the path checks, not a sandbox: a call whose path leaves the grants, a command carrying shell metacharacters, and any command other than the granted `bun test` are rejected before execution, and the Run's frozen authorization commits to the grants and that root. Because a foreground Run has no terminal to answer a prompt, local runs set `tools.approvalMode: yolo`; the grants remain the boundary. Nothing is committed — inspect the diff before accepting a delivery, and point the Graph only at a workspace you are willing to let a model modify.

For the importable `daily-code` Graph, run from a trusted target workspace:

```sh
omp graph import --template daily-code --request-key import-daily-code
omp graph run GRAPH_ID --bindings /path/to/models.md --input task=/path/to/task.md \
  --max-model-calls 30 --timeout-ms 300000 --request-key daily-task-1 \
  --accept-workspace-write --accept-workspace-code --acceptance-check test
```

Terra implements, Sol reviews and edits, and a host-controlled `test`, `typecheck`, or `check` decides bounded rework. The two coding members have no command tool. Both flags explicitly authorize workspace-wide edits and execution of workspace code as the current OS user; path grants are not a sandbox. The template's bindings are in `examples/graph/daily-code/models.md`; use configured providers and models. Run in the foreground; detached dispatch is unavailable for this Graph.

`omp graph templates` lists what ships next to the installed CLI, so a dispatcher never needs a repository path: each row carries the template name, the resolved path, and the same catalog contract the import would expose (`summary`, `in:`, `out:`, `bind:`, `local:`, `deliver:`). A template whose file no longer starts stays listed with an `invalid:` reason instead of being offered silently. `omp graph import --template NAME --request-key KEY` imports one by name; `--template` and `--file` are mutually exclusive, and names are restricted to `[a-z0-9-]` so `--template ../secrets` fails rather than escaping the template root. `graph_read` exposes the same listing as operation `templates` and `graph_manage` accepts `import { template }`, neither of which grants any Run authority.

Graphs that declare `run_input` inputs receive them with repeated `--input NAME=FILE`; each file is published as an immutable Run input artifact and its digest participates in request-key replay, so the same key with different content conflicts instead of silently reusing a Run.

`examples/graph/requirement-spec-draft` is a three-Bot serial pipeline (`frame` → `spec` → `review`) that turns a `task` brief into a specification draft plus a bounded consult answer. It declares `extensions.x-contract`, so `omp graph list` reports its inputs and outputs without reading the full definition. Its nodes are text-only: they neither read nor write repository files, so it produces specifications rather than code, and the implementation slice still needs the sandboxed executor described in the roadmap.

Catalog fields describe the **imported revision**, not the file on disk: a Graph imported before it declared `bindings` keeps reporting `bind:-` until it is imported again with a new request key. That is deliberate — a dispatcher must never hand a Run a bindings path the frozen definition never named — so re-import after changing `x-contract` and dispatch the new Graph ID.

The final node declares `duty: consult`: an ask-only consultant receives one required input and must answer without tools, branching, or reverse questions. The runner enforces the bounds (64 KiB input, 32 KiB answer) and refuses a consultant that holds `read`/`write`/`execute` grants or answers more than one question. Keep long-context summarization on 500K models (Terra/Sol); the 272K consultant is confined to one short question where its higher price is capped.

The binding file is Markdown with YAML front matter mapping `models` names to exact `provider` and `model` values. Configure the corresponding provider login first; the example selects Terra for writing and Sol for review, without a capability or price guarantee. Missing bindings fail before inference; models are never silently substituted.

`run` stays in the foreground and uses the existing Graph scheduler, durable Run/attempt records and immutable artifacts. Bot sessions inherit the OMP default prompt and repository context; their tools are restricted by declared workspace grants. Local runs support serial text-Bot chains and the specifically admitted `daily-code` program-and-bounded-rework topology. Other branching, consultations, loops, programs, queues, child graphs and hard monetary limits remain unavailable. Workspace grants are admission control, not an OS sandbox.

Both provider-request count and deadline require explicit limits. They bound execution, not USD spending; observed usage/cost can remain unknown. Inspect the returned Run identity, state and generated output references/text. Repeat the same command and key to read the original result without inference; changing its intent conflicts. A prior interrupted Run is reported as unresolved, never automatically replayed. Keep the foreground process alive; interruption/deadline is not evidence that remote work never happened. Detached workers and remote/browser execution remain closed.

For work that outlives the terminal, `omp graph dispatch GRAPH_ID --bindings BINDINGS.md --title "…" --report-to bot:orchestrator --max-model-calls N --timeout-ms N --request-key KEY` starts the same Run detached and prints its ID; add `--format json` to receive one `omp.graph/run` object instead of prose (`run_id`, `state`, `graph_id`, node progress, artifact refs, usage, replay flag) for headless adapters. The ceiling accepts 1–64 model calls (default 16) and the deadline at most 10 minutes by default. `omp graph runs`, `omp graph status`, `omp graph notifications --since CURSOR` and `omp graph wait RUN_ID --timeout-ms 300000` then report progress and completions from another process, and the same request key replays the original Run without new calls. Without `--since`, a wait starts at the current outbox head, so it reports only what happens next: a hold or resume you just issued never wakes it, while `--since 0` replays committed notifications. Only terminal, held and stalled transitions are notified — resuming a Run is a control command, not an outbox event, so a dispatcher cannot wake on its own echo. `omp graph monitor --follow` sweeps idle Runs and appends a `run.stalled` notification per idle window, so a watchdog reads stalls from the same outbox instead of polling `runs`. `--report-to` names a Bot mailbox: OMP validates the form only — `bot:<name>` with a lowercase `[a-z0-9][a-z0-9._-]{0,63}` name — before any Run is recorded, rejects a malformed address as `definition_invalid` with no dispatch, and forwards a valid one unchanged. Registration belongs to OMH: `omh mailbox send <bot>` answers `bot_unknown` for a name nobody registered, so a queue never silently waits on a Bot that does not exist. Non-`bot:` labels stay accepted as opaque observer labels.

`omp graph deliver --consumer NAME --command "CMD"` hands each committed notification to an operator command on stdin as one `omp.graph/delivery/v1` envelope, advancing that consumer's durable cursor only after the command exits 0 with `--delivery-timeout-ms` (default 30 s) bounding a single handover. Delivery is at-least-once: a failure returns exit 1 with `delivery_failed` and keeps the cursor before the failed page, so the consumer dedupes by notification id. The command is operator-supplied and never derived from Graph content, and a handover never changes a Run. `--follow` keeps draining until `--timeout-ms`, which makes this the headless push path for a session bridge or a Bot-mailbox forwarder (`omh mailbox send <bot>`).

`omp graph deliver --consumer NAME --builtin inbox` needs no external process: it appends each envelope to `inbox/<consumer>.jsonl` under the profile's graph root with owner-only permissions, fsyncing before the consumer cursor advances, and `omp graph inbox --consumer NAME [--since LINE] [--limit 1..200]` reads pages back as `omp.graph/inbox/v1`. Delivery stays at-least-once, so consumers dedupe by notification id; a full inbox fails with `resource_limit` rather than dropping a record. This is a pull channel — headless clients and the web UI read it whenever they want, but it does not wake an already-running session.

Local execution owns the profile: a second `run`/`dispatch` prints `Waiting for the local Graph host` and waits up to `--wait-for-host` (default 15 minutes, maximum 1 hour) instead of failing with `capability_unavailable`. Preparation — frozen artifacts, Bot definitions and the Run itself — happens only after this process owns the host, so concurrent dispatches never race the profile database and a queued dispatch leaves no half-committed Run behind. Giving up on the wait exits 3 with no Run recorded.

A foreground `hold` parks the executor instead of ending it: `omp graph resume RUN_ID --kind operator` continues the same Run, where the earlier behaviour exited and left the Run `running` with no dispatcher. While parked the executor starts no new dispatch, yet an attempt already in flight may still settle its publish/complete because that work is already paid for. Held time does not consume `--timeout-ms`; only `succeeded`, `failed` and `cancelled` end the process.

A `held` Run records which kind of hold it is, and only an operator pause is resumable by the same principal: `omp graph status` prints `Hold: operator pause`, `Hold: decision gate` or `Hold: reconciliation required` with the command that lifts that kind, and Run summaries carry `hold_kind` without the recorded reason. An approval gate still needs `--decision-ref`; a reconciliation hold (a Bot dispatch whose outcome is unknown) is refused by `resume` with the reason and a pointer to `omp graph recover`, so recovery never masquerades as a pause.

`omp graph recover RUN_ID --reason "…"` closes a Run that is `held` because a Bot dispatch outcome is unknown. It records the intent as finished and never as success, then releases the profile writer that blocks later dispatches. Independent verification of the finished work still comes from `status` and the Run's artifacts.

Bot members act only inside their granted scopes. `read` and `write` entries resolve through `realpath` and must stay inside the declared roots; `execute` accepts only `test`, `typecheck` and `check`, mapped to fixed commands. A grant wider than the dispatch ceiling is rejected during preflight rather than silently narrowed.

The [Graph roadmap](../../openspec/changes/add-omp-graph-execution/roadmap.md) prioritizes M1-A (CLI/OMH template discovery, inventory and result readback) and M1-B (wherdr serial workflow operation) before broader collaboration, requirement-development and screenwriting flows. [Milestone evidence](../../openspec/changes/add-omp-graph-execution/milestone-tasks.md) separates implementation, self-checks, independent acceptance and user acceptance; the original full-scope tasks remain historical.

## Local Graph drafts

`omp graph create NAME` creates an empty local draft. Use `import --file GRAPH.md`, `edit GRAPH_ID --file GRAPH.md --if-revision REV --request-key KEY`, `member add`, `node add`, `connect`, and `permit` to author definitions; mutations other than `create` require a request key. `export GRAPH_ID`, `validate GRAPH_ID`, and `preview GRAPH_ID --format mermaid` inspect the saved revision. Run `omp graph --help` for arguments.

File/stdin Markdown input is bounded by the configured Graph byte limit (standalone: 1 MiB), decoded as strict UTF-8 and never silently truncated or repaired. Oversized input returns `resource_limit`; invalid encoding returns `definition_invalid` before definition mutation or input/answer publication. BOM, CRLF and valid multibyte text are preserved.

Trusted `start --input FILE` publishes the input under the Run key `task`. Both packaged workflow examples bind that key to their node-local `brief` input; embedding callers supplying inputs directly use the same key. This naming does not bypass preflight or enable standalone execution.

The development and screenwriting examples separately declare bounded directed consultation grants and a `consultation-rules` section explaining when to ask each member. These are optional on-demand capabilities, not scheduling edges or gate approvals. The examples grant text-only consultation (two follow-up rounds, three-minute deadline); they add no artifact-sharing scope or file permissions. `GraphRunStore.configureConsultation` intersects deployment policy with the frozen Run's directed grants and limits; editing the draft cannot expand an existing Run, and deployment policy can still deny or tighten access. GraphHost resolves each member's outgoing `when` sections from the bounded, revalidated frozen Markdown into its assignment context; incoming and unrelated sections are excluded, and shared sections appear once. Missing required guidance denies dispatch. Trusted embedding must still enforce artifact scopes and resource reservations and install the continuation runtime; importing or previewing the definition does not do that.

Trusted adapters may select `--format json` for definition mutations, `request get`, `validate`, and `export GRAPH_ID --output -`. The versioned local envelope carries the complete operation or one stored definition snapshot, including its digest and exact Markdown content; stdout is bounded to 8 MiB. Other action/format combinations are rejected before effects. This machine option does not change human Markdown defaults, authorize execution or implement the browser wire protocol.

Trusted profile-local transports can use `GraphWireAuthoringBridge` separately from the read-only observer for protected definition reads, the seven definition edits, and read-only intent reconciliation. Source aliases must share one profile ledger; the Host supplies the principal, immutable source binding, negotiated extension and current expiring grant. Writes require explicit author permission and a live source-ready scope, rechecked synchronously in the mutation transaction. Principal/intent, original request key/content/revision and source binding persist atomically with the definition receipt. Reconnecting under a new scope reuses that intent; stale/history lookup never redispatches. This embedding API adds no listener, browser route, execution control or authentication policy, and does not by itself justify advertising full `graph.execution.v1`.

Intent reconciliation compares the retained original mutation with the request ledger, not just its key. If another mutation owns that key, the conflicting intent stays rejected after reconnect/restart; it cannot inherit the other request's success. Direct CLI key lookup still returns the original key owner's receipt.

`serveGraphWireAuthoringStdio` (`src/graph/wire-authoring-stdio.ts`) is the separate trusted writer driver: supply the bridge's authenticated principal/source/grant options plus byte `input`/`output` Web Streams and an optional parent abort signal. It accepts only the existing exact definition-read, definition-mutation and intent-lookup frames, never negotiates permissions from input, and serializes transactions and replies. Exported limits bound requests/pending input to 8 MiB, pending requests to 16 and replies to 2 MiB; fatal UTF-8/JSON, oversized or unterminated frames close with a generic transport rejection. EOF/abort discards queued work, and a 1–5000 ms write deadline includes backpressure. Keep input open until replies arrive. The driver rechecks current authorization after writable readiness immediately before handing protected bytes to the sink; custom transports must use `GraphWireAuthoringBridge.assertAuthorizedForDelivery` at that same boundary. The trusted sink/parent must discard pending delivery on revocation: already accepted bytes cannot be recalled. Services remain embedding-owned, and a committed write with a lost response is recovered through `request.get` in a new authorized session, not automatic redispatch. The fixed-Run observer and wherdr gateway remain read-only; no CLI writer or public listener is added.

EOF while a reply is unfinished rejects as a transport failure rather than reporting a clean shutdown; intentional parent abort remains cancellation. Neither outcome rolls back an already committed mutation, so recover its original intent before submitting replacement work.

The discoverable `graph_manage` tool provides the same definition-authoring operations: `create` (`name`), `import` and `edit` (`content`), `member.add` and `node.add` (`key`, `value`, `body`), and `connect` and `permit` (`value`). Calls use `version: 1`, a stable `request_key`, an `operation`, `target_id`, `if_revision`, and a `payload` containing those fields. Create/import use null target and revision; changes to an existing definition require its Graph ID and current revision. `content` is GRAPH.md text, not a path. Replay the same request to reconcile it, or retrieve its authoring receipt with `omp graph request get REQUEST_KEY` or `graph_read` using `request.get` and the request key as `target_id`.

`graph_read` can retrieve a definition with `definition.get` and its Graph ID, optionally specifying a revision. It also supports `status` and paginated `events` for existing Runs only when a trusted host authorizes observation; without authorization these reads are denied. Event pages use `after` and `next_cursor`, with a limit of 1–100 (default 50). Execution request receipts are not exposed by this tool. Authorized Run observations also carry bounded `transfers` and `messages` activity pulses (at most 200 each, attempts still live in the frozen definition): handoffs must match a declared edge and a `delivered`/`unknown` state, consultation messages keep only endpoint, kind and a stable ordinal, and entries the definition cannot place are omitted rather than guessed. Pulses describe recorded activity for animation; they are not transcripts and confer no execution controls.

`omp graph report RUN_ID` and the `report` operation return the same `omp.graph/report/v1` document: title, state, the declared deliverable's readiness, per-artifact metadata with a bounded text preview (`--preview-chars` 1–8000, `--preview-lines` 1–100), the newest notifications, and at most three factual next actions. It reads only committed facts, takes artifact content through a separately authorized read-only connection, and treats `ready` as an observation rather than an acceptance.

The Mermaid preview is derived from the definition; solid edges describe task handoffs and dotted edges describe assignments or consultation permissions. Draft authoring does not start or schedule a Graph.

The detached standalone Graph worker and its former `local-policy.json` program policy remain unavailable. The former policy authorized mutable Graph IDs, could revive revoked grants, and could not atomically fence process creation or contain all descendant processes. `omp graph host ensure` and unconfigured asynchronous `start` fail closed even if an old policy file exists. The foreground `run` above is a separate bounded local admission, not permission to enable those executors. Trusted embeddings may configure their own admission, authorization, executor and result-verification capabilities.

Graph Bot preparation freezes the selected binding name, provider, model, revision and an independent in-memory model descriptor. Before each dispatch it rechecks registry availability/authentication and rejects changed request configuration—even under the same provider/model ID—including endpoint, API, wire model, static headers and nested metadata. Session dispatch independently checks its admitted descriptor too. Descriptor changes require new preparation; this conservative check can also hold metadata-only refreshes. Request-time header resolvers remain opaque capabilities: preparation does not execute them, the callback identity is checked, and legitimate refreshed credential values are not frozen. This is not a persisted deployment fingerprint, binding-configuration authentication or repository-rule/permission verification; those remain trusted embedding responsibilities.

Graph tool authorization receives only an independent `{args, toolCall}` snapshot of the prepared call, plus its abort signal—not the live tool, session or model history. The policy must throw to deny; rewriting this snapshot cannot redirect execution. Ambient hook argument replacements are rejected, and only passive context captured before authorization is returned afterward, so a retained hook result cannot introduce a late replacement. Ordinary Bot hooks keep their existing behavior. Trusted hooks and tool implementations still require their own enforcement; this boundary is not an OS sandbox or production admission policy.

Trusted Hosts sample cumulative usage from the exact durable Bot Job admission into a per-attempt ledger; snapshots replace prior totals instead of adding them again. `observed_bot_usage` includes token counts; authorized `status`/`watch` show known USD subtotals and completeness for observed Bot jobs only. Unknown calls remain partial/unknown; these samples exclude unobserved jobs and non-Bot costs, and are neither a final bill nor a hard spending limit. Accounting replay/recovery does not authorize execution.

Contained child Bot observations also refresh the parent's subtotal atomically from original per-attempt ledger rows, not by adding child subtotals again. Replay adds no charge or budget consumption. This accounting works for retained historical child work but does not enable new child execution or supply monetary reservation authority.

Authorized local observation snapshots include captured Bot usage and each invocation's declared selected outcome independently from execution state. Retained historical replacements expose only facts captured at that revision; missing old usage/outcome is unavailable, not backfilled from a later Run. Read/history arguments and returned cursors are detached across asynchronous authorization checks.

The observation core includes a full-record SQLite ledger (`wire-ledger.ts`), authorized graph-source frame sessions (`wire-session.ts`) and the bounded source-state consumer in `@oh-my-pi/pi-wire/graph`. It validates base records and the six execution record kinds. Execution records require an explicitly negotiated extension and supporting source; legacy sessions retain base records and verified cursors. Publishers share their authoritative write transaction; read-only observers cannot install a missing ledger or publish history. Snapshots commit after all pages and end; reconnect hides retained content until reauthorization. The wherdr canvas consumes the authenticated WebSocket relay through the shared native consumer, separately from captured HTTP history; opted-in sources additionally show read-only execution records. Full execution controls and production execution admission remain unfinished.

Live subscriptions recover an expired cursor or replaced source journal through a fresh authorized snapshot of that source only. Its previous image remains visibly syncing until the snapshot commits; replay then reaches a verified ready watermark without resetting unrelated sources. Record revisions from a previous journal do not override the replacement epoch. This does not repair retained historical gaps or grant mutation authority.

Browser bundles can import `GraphWireSourceState` and protocol types from the zero-runtime-dependency `@oh-my-pi/pi-wire/graph` package entry without installing the agent or coding-agent packages or loading Host, SQLite, native bindings or provider runtimes. The consumer uses the producer's canonical serializer and record validators, not a frontend copy. Shared Graph identities and state vocabularies are owned by that same browser-neutral package; authentication, execution and persistence remain host responsibilities.

Trusted start preflight may supply `observation: {source_id, members: {[memberId]: {bot: {source_id, profile_id, bot_id}, config_revision, model_binding_ref}}}`. The store freezes these identities and publishes topology, execution members, invocations and scoped counters atomically with admission. Subsequent schedule and consultation mutations publish coherent lifecycle replacements in their own authoritative transaction; unchanged records are not republished. Ready nodes have no invented attempt; actual Bot Job and program execution identities survive unknown recovery and cannot be replaced. Auxiliary consultations publish conversations, not fake topology nodes or Jobs; message text remains protected. Bot configuration revisions differ from model-binding revisions. Host admission and recovery check actual Bot/profile/configuration; children inherit only their frozen member subset. Sources cannot be reassigned, and legacy Runs are not backfilled with missing provenance or execution history. Production CLI admission and full protected-detail/control integration remain unfinished; this embedding API grants neither standalone execution nor observation access.

The read-only `GraphWireReadBridge` accepts protocol frames only after an out-of-band authenticated embedding supplies a current source catalog and scope grants. It implements negotiation, authorized subscriptions/replay, Run discovery and retained history; history tokens bind the connection, authorization generation and full query, pin watermarks and expire within 60 seconds. A separate consultation reader resolves only published message refs within the exact source/Run and verifies stored text digests; it cannot read snapshots, credentials or arbitrary files. Reads recheck authorization before releasing results, and all execution/authoring mutations are rejected. Default negotiation excludes execution records; trusted embeddings explicitly opt in. The embedding owns authenticated transport, origin checks, cadence/backpressure and immediate revocation; wherdr's relay implements its own bounded connection without changing Passkey admission.

Trusted embeddings may additionally inject `GraphWireArtifactContentReader` backed by their existing artifact store. It resolves only explicit artifact-bearing references published within the exact source/Run and matched to persisted inputs or outputs; binding/attempt outputs must belong to that attempt. It returns complete bounded UTF-8 text with BOM and line endings preserved, verifies immutable bytes and current artifact grants, then rechecks the published reference, persisted input/output identity and metadata before release; the bridge separately rechecks connection authorization. Withdrawn inputs or replaced attempts cannot release a stale in-flight read. Missing/expired content remains unavailable; binary, malformed, oversized or unresolved content is not truncated or repaired. Snapshot/model/credential references and arbitrary filesystem paths are not readable. This optional reader does not enable production execution negotiation.

The shared local artifact store also re-resolves registration after file retrieval and final asynchronous read authorization. Withdrawn availability, elapsed expiry, disappeared registration or changed immutable metadata withholds the bytes across all consumers, not just wire reads. This is a final read check, not atomic revocation of content already delivered.

For selected Bot-to-Bot edge mappings, the Host freezes source attempts and artifact refs into a readable Markdown handoff attached to the downstream mailbox input. A Transfer becomes `delivered` only after the exact durable Bot request, Job, Graph context and queued input are verified; the confirmation and wire publication share one fenced Graph transaction. Dependency satisfaction and artifact publication are not delivery. Unconfirmed admission remains unknown, non-Bot endpoints do not acquire fake Bindings, and retries preserve earlier transfer identities. Delivery proves mailbox admission, not artifact consumption, model execution or business acceptance.

Dependency observation evaluates each frozen edge separately, including its outcome, persisted budget suppression and any-join winner. Sharing an upstream invocation does not satisfy an unselected edge or attach evidence to it; these decisions are distinct from confirmed mailbox delivery.

Trusted local launchers can use the private JSONL source `omp __omp_worker_graph_wire_read [--execution-records] ROOT SOURCE_ID RUN_ID [RUN_ID...]` (or invoke `graph/wire-observer.ts` directly outside a CLI installation). The optional flag must precede ROOT and permits negotiation of `graph.execution.v1` read records and scoped consultation text, not execution. Without it, base records remain available and filtered execution events only advance watermarks. The embedding equivalent is `executionRecords: true`; artifact text still requires a separately injected trusted artifact reader and is unavailable through this CLI source. Fixed launch configuration authorizes only named Runs, not the whole roster; client frames cannot select another profile/source or dispatch commands. Keep stdin open while consuming replies: EOF or an embedding abort revokes the connection. Request lines are limited to 64 KiB, pending input to 16 requests/128 KiB and output frames to 2 MiB; slow writes have deadlines, polling is at most five seconds apart, and an overlong delivery closes instead of overlapping operations. The wherdr backend can launch it using trusted `wire_command`, fixed source/Run scope and current-session/configuration reauthorization. Its live canvas renders negotiated execution summaries and explicitly requested consultation text, not arbitrary artifact content or execution controls. Consultation reads require exact request/source/Run/reference correlation and shared frame validation, with a 1 MiB UTF-8 text ceiling. The browser displays one detail at a time as inert text without persistent caching; timeout, stale state, reference withdrawal, lock, hidden page, disconnect or scope changes clear the detail and pending request.

Run observation (`status`/`watch`, the corresponding `graph_read` operations and the local wherdr observer) opens an existing private profile read-only rather than constructing a Host store. Missing profiles/databases, unsafe ownership/permissions, symlinks and replaced database identities fail closed; reads do not create profiles, repair permissions or install/migrate Host tables. Writer and observer queries share snapshot digest and frozen-definition validation.

`policy.cost_limit` remains readable in drafts but execution currently rejects it with `capability_unavailable`: no trusted monetary reservation authority is installed. Restored limited Runs are held before fresh scheduling, consultation or dispatch; Bot turn fences reject such ceilings too. Do not remove a requested ceiling merely to make a workflow run. Actual price reservation/enforcement and any explicit operator-approved limitation remain unfinished.

Trusted hosted Runs retain queue identities through reconciliation failures; a temporary denial holds advancement without discarding future authorized reconciliation. Confirmed queue terminal results and Bot cleanup are persisted before cancellation can finish. Prior-epoch Bot cleanup requires the current Host, the recovery worker's retained lease and exact durable admission identity; it never replays input or turns a lost runtime into success. Open human waits can be withdrawn atomically without deleting questions or accepting late answers. A cancelled Run never routes a late success to downstream work. Unconfirmed effects still keep cancellation unresolved; standalone execution remains disabled.

Successful attempt admission and dependency routing share the declared outcome/verdict and output-reference checks. A result missing required outputs or containing malformed or undeclared refs is retained as a rejected observation, not a successful invocation; restored historical results are checked before routing too. These checks do not replace artifact content, schema or access verification.

Queue callback authorization receives an independent observation copy. Host result verification and artifact-preparation callbacks receive separate dispatch/result copies, and verified completions are snapshotted before later awaits. Callback mutation cannot change authenticated service state, inject result references or alter the Bot candidate/outcome committed by the Host.

Queue nodes enter durable `waiting` after submission settles, releasing Graph execution capacity while the external service owns the work. An observed Run's wire invocation carries `wait_reason: queue:<state>` from the exact persisted queue attempt, including remote terminal results still awaiting Host verification. Queue updates and feed replacements commit together; repeated observations and reads do not republish unchanged records. Remote success alone neither completes the invocation nor satisfies dependencies; verified completion clears the wait reason. Historical views retain the original queue state, without exposing raw remote task IDs.

Integration acceptance has a durable execution ledger. Cancellation waits for its confirmed completion, retains late observations as nonpassing evidence and prevents execution if cancellation occurs during preauthorization. Uncertain execution or a lost Host remains unresolved after restart; elapsed time and a rejected callback do not prove termination. This does not add process containment to the local acceptance adapter.

Trusted embeddings can recover a recorded execution without rerunning validation: the current owner calls `getPendingIntegrationAcceptanceExecutions`, resolves the exact `{run_id, execution_id, freeze_id}` against its own durable executor binding, and only after independently confirming the execution and its effects stopped calls `reconcileIntegrationAcceptanceExecution` with that identity, a durable termination reference and an observation. Store-backed `AcceptanceHost.run` receives the identity as its second argument so a recovery-capable executor can persist the binding **before launch**. The store checks identity and ownership, not the truth of the external termination reference; this trusted API is not exposed as a model tool. Missing reliable stop knowledge must remain pending. A PID check, timeout, process leader exit, injected callback or model statement is not scope-complete termination proof. Reconciliation atomically records a nonpassing HOLD receipt, retires the pending execution and settles cancellation when otherwise safe; active Runs become held. Identical retries return the original durable receipt without another revision; conflicting results and late original callbacks cannot overwrite it. No automatic validation replay, source isolation, standalone execution or contained-child execution is enabled.

The subprocess smoke exercises real local execution, not post-restart external termination proof. To exercise recovery with a real executor, persist the supplied identity with its external execution handle before launch, interrupt the Graph Host after dispatch but before receipt commit, restart and claim a new owner, inspect the same pending identity, then obtain the executor's authoritative scope-complete stop record and submit it once. Repeating that exact submission must return the same receipt; changing any identity or observation must fail without state changes. If the executor cannot supply that stop record (including descendant/effect coverage), leave the execution unresolved; the local adapter cannot supply it.

Acceptance policy and execution callbacks receive independent request copies; their mutations cannot change the frozen version or the command, tester and scenario recorded as evidence.

Trusted child recovery failures block new admissions without blocking cancellation or reconciliation of existing owned work. Temporarily unavailable authentication preserves existing child dispatch records for retry. Scheduling reauthenticates a recovered child against its exact open attempt, current parent reservation and enforced isolation within the ownership transaction; it does not authorize new subgraph dispatch. Cancelling containment preserves a child's already-confirmed success or failure instead of rewriting its historical result.

`GraphRunStore.resolveChildParent` verifies the frozen member, exact dispatch inputs and all scoped budget/loop reservations from durable scheduler state; a callback's `reserved: true` is insufficient. Store child creation, recovery and scheduling intersect that proof with the trusted adapter's narrower authorization. `resolveChildRecoveryIdentity` retains the persisted old fence for reconciliation only, including missing reservations so existing work can be cancelled. Neither helper grants executor, role or isolation capabilities, creates a child Run, or enables new subgraph dispatch.

`GraphRunStore.createInheritedChildExecution` can atomically create a durable child Run and containment record through a trusted adapter: it reuses frozen parent member/executor bindings and authorization, forwards only referenced artifact inputs from the parent's ready snapshot, and creates no imports or independent budget. Missing or text-valued `run_input` references are rejected; literal text remains available in node definitions. Creation alone grants no dispatch authority; ordinary child scheduling and claiming require explicit serial writer admission below.

`createChildExecutionFromArtifact` accepts a planner's registered `text/markdown` artifact only through a named frozen parent-ready input. It verifies authorized UTF-8 bytes, policy, exports and unchanged parent/artifact facts, then saves the child and exact plan provenance atomically. Replay cannot replace that provenance. Creation alone grants no execution authority; optional trusted serial authority also admits the child writer and accepts the exact parent dispatch in that transaction.

Inherited child creation also freezes explicit parent-output to child-node/output bindings. Required parent outputs need compatible declarations; replay cannot change the bindings. `getChildOutputCandidates` selects only unambiguous confirmed scheduler results after the child succeeds, not artifacts by matching names. Candidates are not proof of readable, available or schema-valid content, passing integration acceptance, or permission to complete the parent.

`verifyChildOutputCandidates` additionally checks the exact producer attempt, media type, authenticated immutable bytes and supported declared schema. It rechecks parent/child state after asynchronous reads and discards candidates on cancellation or version drift. Every explicitly bound export must resolve, including optional parent outputs; omit the binding to leave an optional output absent. This verification does not prove integration acceptance or complete the parent.

Trusted embeddings can call `admitSerialChildWriter` with exact parent/child revisions and an independently established whole-parent stop observation. A queued serial child with `max_parallel=1` then borrows the root profile writer reservation; parent siblings and other Runs cannot acquire it, no child budget is minted, and restart does not release it. Known active sibling, consultation, acceptance or descendant effects reject admission. This is cooperative Graph admission, not an OS sandbox or proof supplied by a reference string.

`aggregateSerialChildExecution` verifies exact child artifacts and invokes a synchronous trusted integration gate with an independent proof copy. Current owner/version/availability checks, child stop receipt, parent completion, containment and replay receipt commit atomically. Identical historical replay does not reintegrate. Successful children retain their scope until aggregation; standalone release is allowed for reconciled failure/cancellation cleanup, not to strand successful integration. Recovery preserves succeeded children awaiting integration and discards stale scheduler snapshots after reentrant lifecycle callbacks. Standalone execution remains unavailable; neither workflow is yet runnable end to end.

A held parent retains existing child work without integrating success. Confirmed stopped child failure may settle as failure; HOLD alone is not revocation. Explicit cancellation, lost authority/reservations or unenforced isolation propagates cancellation.

Trusted `GraphHost.child` adapters can explicitly authorize automatic serial subgraph dispatch. Admission is checked before budget consumption, at claim and before child persistence; callback lifecycle changes are preserved, not overwritten by stale scheduling or rolled back with speculative child writes. The adapter resolves only a frozen planner input and independently establishes parent quiescence, executor/isolation enforcement, child stop and integration. No configuration is inferred from Graph prose or exposed by standalone CLI.

Host collection retains successful children until trusted integration accepts them, and settles failed/cancelled children only with exact stop evidence. A late success under parent cancellation is recorded without starting downstream work. `reconcileUnstartedChildDispatch` separately reconciles unknown dispatches with no containment after independent stop observation; it never replays work, refunds budget or certifies success. Root writer admission remains held until whole-family reconciliation.

Child policy and coordination callbacks receive independent definitions, member grants, identities and isolation disclosures. Mutating those arguments cannot replace the validated executor or change the durable parent/isolation record.

Normal approval paths do not wait for a dormant final-review or budget-exhaustion handler once every possible activator has settled without selecting it. Unfinished, missing or ambiguous activators do not bypass the handler.

An upgrade cannot stop a previously launched worker running old code. Before relying on the new fail-closed behavior, an operator must revoke its old policy, stop the detached `omp.graph.host` service and independently reconcile any processes it launched, including descendants. A process group alone is not a sandbox.

Hosted non-human execution reserves a durable, profile-wide writer admission for its entire Run; human questions do not reserve it. Other Runs wait before consuming dispatch budgets, and acceptance and independent consultation cannot bypass it. HOLD, Host restart and even a successful Run do not release the reservation: the current trusted embedding must independently establish whole-Run scope quiescence, inspect `getProfileWriterAdmissions` and submit the exact terminal Run revision to `reconcileProfileWriter`. Identical reconciliation replays return the original receipt without releasing another Run. Legacy executed Runs are conservatively reserved during migration. This is Run-grained cross-Run exclusion, not intra-Run writer/path enforcement, a descendant sandbox or an automatic stop verifier; standalone and child execution remain disabled.

`TrustedProgramExecutor.registrationRef` and `verifyRegistration` let a trusted integration freeze and compare a digest of the registered program configuration. The host requires a matching frozen reference and registry verifier before program dispatch; an unavailable or changed registration is not dispatched. The integration must use the registered reference in trusted preflight and separately ensure executable and script integrity: this configuration digest does not verify their bytes, authenticate an operator, or establish an authorization grant.

Trusted program registrations must explicitly supply `env`, the complete child environment; omitted or malformed environments are rejected. Include any required `PATH` and other values explicitly, and do not use this configuration for secrets: the registration digest is not a confidentiality mechanism. This limits inherited environment exposure but does not prevent a process from accessing other host resources, contain descendants, or fence grant revocation against spawn.

Program resolution, result verification and artifact preparation receive separate dispatch/result snapshots. The Host retains the executor's original terminal state and artifact refs, and snapshots the verified completion before later awaits. Mutating callback arguments or a retained completion cannot turn a failed program into success, replace its outputs or change the dispatch identity; mismatched registration remains unknown/held rather than delivered.

Program dispatch caps the resolved `timeout_ms` at the frozen node's declared `timeout_ms`; the executor also retains its registered timeout and absolute deadline, so the shortest limit wins. This program-specific bound does not establish generic Bot/queue deadlines, descendant termination or automatic retry safety.

Trusted embeddings can close an unknown program dispatch with `reconcileProgramExecution`: independently confirm that the exact persisted `{run_id, intent_id, invocation_id, attempt_id, fence, request_key}` execution and its effects stopped, then submit that identity, the current Run revision, a durable termination reference and observation. Only the current owner can commit; the receipt records failure with HOLD, or cancellation when requested, preserving the prior observation without publishing outputs or replaying work. Identical submissions return the original receipt across restarts; conflicting facts reject. This is not a model tool or stop verifier, and does not release the separate whole-Run writer reservation.

Bot dispatch/recovery, queue resolution and optional human-node inspection also receive independent dispatch snapshots. Queue requests are captured before asynchronous authorization, so a resolver's retained envelope cannot alter the request identity or inputs subsequently submitted.

Hosted Bot replies retain the original request key, question and answer before asynchronous admission. Admission callbacks inspect independent reply/dispatch copies; their mutations or caller changes during authorization cannot replace the answer delivered to the Bot or invalidate its attempt.

Local artifact reads check trusted access policy both before retrieval and before returning the verified content; this does not make revocation atomic with delivery. Requests, resolved metadata, buffered publication bytes and streamed chunks are captured before asynchronous policy or file work; policy callbacks receive independent scope arrays and cannot retarget reads, alter authenticated bytes or widen publication scopes.

Trusted program outputs with `schema_ref` are checked before dispatch (including absent optional outputs) and against the original bounded file bytes before publication completes. Schemas are authorized immutable JSON artifacts. Validation never coerces, inserts defaults or removes keys. The strict 2020-12 subset supports acyclic local JSON-pointer refs and ordinary type/object/array/combinator/string/numeric-bound assertions; unsupported keywords/dialects, recursive/external/dynamic refs, `$ref` assertion siblings, format/content/unevaluated assertions, `nullable` and `multipleOf` fail closed. This is not full JSON Schema support. It does not add program isolation or enable standalone execution.

Strict schema admission also bounds JSON tree depth/size and expanded reference paths; excess fails validation. See the Graph contract for exact limits. These are traversal limits, not a regex execution deadline or an OS sandbox; registered schemas are trusted configuration.

An embedding with authenticated human-decision and immutable artifact policies can expose `omp graph answer RUN_ID --decision DECISION_ID --file answer.md --if-revision REV --request-key KEY`. The file's YAML front matter requires `outcome` and `input_digest`, with optional `verdict`; its Markdown body is the answer. `--file -` reads stdin. This admission is not configured by the production CLI; without it the command fails closed.

Trusted CLI and `GraphReadTool` embeddings may install a separate synchronous `authorizeExecutionReceipt` gate to read saved start/answer/hold/resume/cancel and text-publication receipts with `request get KEY`. The gate receives a detached copy of the original request, including its original target, revision and payload; only `true` permits delivery. Lookup never rereads task files, performs preflight or redispatches work, and a saved rejection is a successful read, not a successful Run. This permission does not grant Run observation, publication or execution. Without it, protected receipts stay private; definition receipts retain ordinary profile access. Private observer/authoring transports and standalone CLI do not acquire this permission.

`GraphManageTool` embeddings may separately install `lifecycle: {principal, policy}` to hold, resume or cancel Runs through the same transactional lifecycle API as the CLI. Read/receipt permissions grant no control. Requests require the Run revision; resume requires a verified immutable decision, every replay is reauthorized, and cancellation does not certify external work stopped. An explicit `start: GraphStartPolicy` grants typed start admission through the same service as CLI start: authorized published input refs, current target/request permission and trusted preflight are required. A replay returns the original Run before current-draft preflight. Built-in tools have neither grant.

An explicit `answer: GraphAnswerPolicy` lets `GraphManageTool` submit an already-authorized human decision through the same typed admission and transactional answer ledger as CLI answer. Requests carry the decision ID, input digest, outcome and published content reference; optional verdict and evidence references remain part of receipt identity. The trusted embedding resolves bounded immutable answer bytes, authenticates the author and rechecks current human policy inside the commit, including on replay. Agents cannot supply their own human identity, bypass approval or gain answer permission from read/start/control grants. CLI publication uses the actual authorized Markdown body. Caller and policy argument mutations cannot retarget the submitted answer.

With a separate trusted `publication: GraphTextPublicationPolicy`, Agent tools can submit `artifact.publish` with text content, media type and an optional expected digest (explicit `null` when absent). CLI embeddings additionally authorize the target before reading `omp graph artifact publish GRAPH_OR_RUN_ID --file task.md --media-type text/markdown --request-key KEY`; `--file -` reads stdin and `--expected-digest sha256:...` verifies content. Readable output includes `Artifact: ID@DIGEST`. Provenance and access scope come from trusted policy, never model arguments. Publication registers verified immutable bytes and the global receipt atomically, without editing a definition or advancing a Run. Replays require current synchronous permission and return the original reference without republishing; protected receipt lookup needs its own read grant. Existing artifact policies cannot be silently replaced: configure text publication only on a fresh Store. Invalid/unadmitted or unauthorized requests do not reserve keys; admitted application rejections are retained, infrastructure failures may leave only unregistered orphan files. Standalone and built-in defaults remain closed.

Newly committed human answers include a content-addressed ledger evidence reference. Trusted embeddings can use `GraphRunStore.getHumanEvidence` to read it with decision, Run, invocation, input digest, source revision, outcome, and author identity matched exactly; each read is authorized by the configured human policy. This is historical decision evidence, not an artifact or a modification grant. Callers must independently verify current applicability and enforce the authorized modification scope; the standalone worker provides neither screenplay protection enforcement nor production human authorization.

Trusted embeddings can configure `GraphRunStore.configureScreenwritingPublications()` after human and artifact policies. The current Host issues a single-use authority with `issueScreenwritingPublication(ownerId, epoch, authority)`; `prepare(author, request)` builds the candidate from approved immutable inputs and bounded byte replacements, and `commit(token)` atomically registers that exact artifact and its replay receipt. Current owner, Run revision, approved invocation/input versions and revocation are checked at commit. `revokeScreenwritingPublication` permanently disables unused authority; a new request key cannot reuse its approval. This enforces byte scope, not semantic story constraints. Protected revision nodes, proposal presentation and automatic Graph dispatch remain unavailable.

After independently confirming executor termination, trusted embeddings may call `completeScreenwritingPublication(ownerId, epoch, token, target)` with the exact Run/invocation/attempt/fence, output name, outcome and optional verdict. Only Bot/program tasks pinning both approved inputs and declaring the matching media type are accepted; schema-bound outputs currently reject on this composition path. Registration, authority consumption, task completion and the durable target binding commit together or all roll back. Reconciliation under the current owner returns the original reference without another transition; retargeting conflicts, and a standalone publication cannot later settle a task. This is not an automatic revision dispatcher, termination verifier or semantic approval check.

An embedding with trusted start admission may pass `--from NODE --provided FILE` to import previously authorized outputs. FILE is Markdown whose front matter contains `outputs: {node: {output: {id: ..., digest: ...}}}`; the preflight must independently verify provenance, applicability and authorization. `--provided -` reads stdin, but cannot share stdin with `--input -`. The standalone local program policy does not support imported outputs.

## Memory backends

The agent supports three mutually-exclusive memory backends, selected via the `memory.backend` setting (Settings → Memory tab, or `~/.omp/config.yml`):

- `off` (default) — no memory subsystem runs.
- `local` — existing rollout-summarisation pipeline; writes `memory_summary.md` and consolidated artifacts under the agent dir.
- `hindsight` — talks to a [Hindsight](https://hindsight.vectorize.io) server (Cloud or self-hosted Docker), retains transcripts every Nth user turn, recalls memories on the first turn of a session, and exposes `retain`, `recall`, and `reflect`.

### Hindsight quickstart

1. Run a Hindsight server (Cloud or `docker run -p 8888:8888 ghcr.io/vectorize-io/hindsight:latest`).
2. Set `memory.backend = "hindsight"` and `hindsight.apiUrl = "http://localhost:8888"` (or your Cloud URL).
3. Optional environment overrides (env wins over settings):
   - `HINDSIGHT_API_URL`, `HINDSIGHT_API_TOKEN` — connection
   - `HINDSIGHT_BANK_ID`, `HINDSIGHT_DYNAMIC_BANK_ID`, `HINDSIGHT_AGENT_NAME` — bank addressing
   - `HINDSIGHT_AUTO_RECALL`, `HINDSIGHT_AUTO_RETAIN`, `HINDSIGHT_RETAIN_MODE` — lifecycle
   - `HINDSIGHT_RECALL_BUDGET`, `HINDSIGHT_RECALL_MAX_TOKENS` — recall sizing
   - `HINDSIGHT_BANK_MISSION`, `HINDSIGHT_DEBUG`

Switching backends mid-session immediately replaces the live backend, memory tools, listeners, and system-prompt context. Existing users with `memories.enabled = true|false` are migrated to `memory.backend = "local"|"off"` exactly once on first launch; afterward, `memory.backend` is the sole runtime selector.
